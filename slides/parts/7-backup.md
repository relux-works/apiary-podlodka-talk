# Состав скилла *у агента*

<DiagP34SkillAnatomy reveal />

<p class="lead" v-click="6">Агенту — инструкции и шим; исходники, тесты и хуки пакета в контекст не попадают.</p>

<!--
[Иван, на вопрос «что такое скилл с командой»] Что такое скилл с командой. Скилл у нас — git-репозиторий на теге. Агенту достаются только инструкции: SKILL.md, references, examples. Команда объявляется в agent-skill.json одним из трёх способов: скрипт из объявленной папки; системная утилита, которую Curator только проверяет — нет git на машине, установка откажет с подсказкой; или исходник на Go, который Curator собирает сам, закрытым драйвером, без сети и без хуков. # Установка скилла — *цепочка проверок*

<DiagP34InstallGates reveal />

<p class="lead" v-click="7">Разрешение, проверка и аудит — потом одна транзакция; код пакета не исполняется.</p>


<!--
[Иван, на вопрос «что проверяет установка»] Как Curator ставит такой скилл. Это пакетный менеджер, только с воротами. В Skillfile.json у каждого скилла ровно одно из трёх: тег, ветка или ревизия. Тег превращается в коммит, зависимости разрешаются по цепочке, и у одного имени во всём дереве ровно один коммит. Дальше проверка: SKILL.md с правильным именем, манифест по схеме, пути без ссылок наружу, никаких коллизий имён, нужные системные утилиты на месте. Потом аудит: хэш всего дерева, статическая канарейка, детекторы, записи реестров, и отзыв блокирует всегда. Собирать Go Curator начинает только после аудита. И только потом одна транзакция публикует контекст, команды и маркер с коммитом и хэшем. Любой отказ раньше не меняет на диске ничего. Главное правило: код пакета при установке не исполняется вообще — мы проверили, postinstall из package.json так и не запустился.

Честно про умолчания: сегодня проектный аудит по умолчанию только предупреждает, строгий режим — одна настройка. Решено, что неизвестные источники будут отвергаться по умолчанию.

Источники: curator-spec v1.0.0-rc.13 profiles/manager.md §2 («Package code MUST NOT execute during any phase»; планирование только на чтение и одна сериализованная публикация), §2.1 (фазы по порядку: снимок, манифест, замыкание, коллизии и system-зависимости, аудит и реестры, и только после всех ворот — сборка), §2.5 (отказ сохраняет установку байт в байт), §7 (хэш сырого дерева, канарейка, детекторы; «local hash or source revocation always blocks»; pin не перебивает отзыв), §7.1 («a hostile repository plus curator install passes with zero blocking gates under defaults»; security_posture: hardened; ревизия A предупреждает security_posture_permissive, ревизия B позже сменит умолчание); protocol/core.md §3, §5 (ровно одно из tag, branch, revision), §7 (одно имя — один коммит, цикл — ошибка), §8 (sha256 содержимого), §10 (маркер); protocol/registry.md §4 («Revoked always blocks»); curator v0.15.0-rc.2 docs/cli.md (--strict-tags: сдвинутый тег — ошибка; status --check); wiki book/ru/06-curator.md («неизвестные источники по умолчанию отвергаются» — ⟦решено⟧); живая проверка rc.2 29.09 (.temp/review/F-curator-diagrams.md, F.0: postinstall из package.json не выполнен; install --audit strict проходит). # Кафе *как плейбук*

<DiagP5Cafe reveal />

<p v-click class="lead">Ядру не нужно знать, что такое кафе: владельцы, поля, таймеры и события — данные плейбука.</p>

<!--
[Иван, на вопрос «как выглядит процесс не про разработку»; демо кафе убрано 12.10] Главный тест общности: машинка не обязана быть про код. Пример из спеки — заказ поставщику в кафе.

Черновик пишет агент-закупщик. Одобряет менеджер, человек, и это состояние агент покинуть не может. Отправку ведёт инструмент — команда портала поставщика. Инструмент в плейбуке — это команда из скилла: Curator её поставил и проверил, а запускает её исполнитель ядра, не агент. Иначе запуск мог бы подложить в PATH свою программу с тем же именем и подделать проверку. Подтверждение приходит подписанным событием поставщика, пятнадцать минут тишины — эскалация менеджеру. Счёт уходит другому процессу, бухгалтерии, и результат возвращается событием.

Четыре цвета — четыре вида владельцев: агент, человек, инструмент и другой процесс. Данные тоже становятся маршрутами: в спеке есть пример guard'а «заказ дороже 500 евро — к менеджеру», а в кафе к менеджеру идёт каждый заказ. Одобрение привязано к отпечатку полей, так что заказ, одобренный на 620, не уйдёт на 6 200.

Внизу следующий пример не из разработки — ВНЖ в Грузии. В спеке его ещё нет, это видение.

Статус: кафе с бухгалтерией лежит в спеке и проходит схему. Живое демо — после вехи, где у ядра появятся инструменты, таймер и подписи, и после поправки waggle для нескольких машин.

Источники: curator-playbook examples/cafe/ (cafe.playbook.json — воркфлоу purchase: каждый черновик идёт в approval, таймер PT15M, расписание weekly-inventory; bookkeeping.playbook.json; project.Playbook.json — «the cafe demo follows the waggle amendment, CM2, and PC3»); spec DRAFT v4.8 §4.2, §6.3 (guard field, порог 500 € — общий пример), §6.4 (620 → 6 200), §6.5, §6.9, §6.11 (инструменты запускает исполнитель ядра из хранилища Curator, не шим из PATH; находка опровергателя v1 N7), §15 (демо кафе — после PC3 и поправки waggle); техническая записка, глава 03 («иначе run доказателя мог бы подложить свой lean в PATH»); пост, раздел 5.1; wiki research/call-digest-2026-09-keeper-concept.md §3.8 (ВНЖ). # Вход внешнего агента *в рой*

<DiagV4DOnboard reveal />

<!--
[Иван, на вопрос «как чужой агент к вам попадает и чем вы защищены от подмены»] Донор получает приглашение — по тому каналу, которым он нас нашёл: адрес нашей точки присоединения, отпечатки нашего корня и SSH-хоста, проект, роль, срок и одноразовый код. На его машине одна команда заводит мост, и мост делает три ключа по ролям: подпись, расшифровка пакета, SSH. Ключи живут у моста, не у агента.

Точка присоединения выдаёт серверный challenge, и донор присылает подписанный транскрипт: три ключа, challenge, код. Приглашение потребляется один раз. От подмены при первом контакте защищают три якоря, которые обязаны сойтись: сертификат домена точки присоединения, отпечатки из приглашения и DNSSEC-записи нашей зоны, которые клиент проверяет сам.

Дальше мы закрепляем три ключа в реестре, корень подписывает допуск, выдаём гранты: писать в свою ветку, читать свой ящик, до какого срока, без права передавать дальше. Пакет — наш корень, сертификат оператора, адрес хоста и ключ SSH-хоста, имя пользователя рабочего места — шифруем на его ключ расшифровки, и донор забирает его у точки присоединения по второму challenge. Личности носителя и токенов в пакете нет: в Matrix за работника говорит наш мост.

Рабочее место — пользователь ОС без пароля и входа; его ключ SSH лежит в файле вне дома пользователя, с принудительной командой-исполнителем. Ключ нашего хоста мост донора сверяет при каждом подключении. Первым он пишет подписанное «готов».

[Для себя] Сверка отпечатка голосом убрана решением 10.10: донор ничего не настраивает; второго человеческого канала нет, приглашение идёт тем каналом, которым донор нас нашёл. Кто начинает онбординг — человек-владелец машины.
